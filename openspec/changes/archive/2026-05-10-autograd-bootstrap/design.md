## Context

`packages/gpu` ships device bootstrap, a `KernelRegistry`, and registered forward kernels (`core.matmul`, `core.add`, `core.mul`, `core.scale`, `core.gelu`, `core.transpose`, `core.reduce_sum`, `core.reduce_max`, `core.softmax`, `core.rmsnorm`). `packages/tensor` exposes a functional surface (`createZeros`, `createFromArray`, `toArray`, `destroy`, `matmul`, `add`, `mul`, `scale`, `gelu`, `transpose`, `reshape`) that routes to those kernels via the `core.*` IDs. `packages/autograd` is still a single-symbol stub. `docs/sequential-change-proposals.md` step 5 sequences **autograd — graph, topo backward, parameters** next, with the explicit guidance to add backward coverage **pairwise** with forward kernels rather than landing every gradient at once.

`docs/project.md` Component 3 sketches a class-based shape (`class Variable`, `interface Operation`, `ParameterRegistry`). This change deliberately picks a **functional** record-and-free-function surface consistent with `packages/tensor` (the layer immediately below) and with `docs/guidelines/typescript.md`'s "functional first" stance. The single intentional mutability is the `Variable.grad` slot — accumulated during `backward` — documented at the type level and concentrated behind a single `accumulateGrad` helper.

This change implements **only** the autograd ops whose backward is **trivially derivable** from existing tensor surfaces: `add`, `mul`, `scale`, `transpose`, and `reshape`. `matmul` backward needs `tensor.matmul` + `tensor.transpose` chained correctly with broadcasting-free shape handling and lands in its own change. `gelu` / `softmax` / `rmsnorm` backward each need either a derivative formula or a dedicated gradient kernel and land pairwise alongside their forward analyses. `embedding`, `cross_entropy`, optimizer kernels, and `clip_norm` are out of scope per `docs/sequential-change-proposals.md` steps 6 / 7.

Constraints from existing specs:

- **`monorepo-skeleton`** still requires the root `lint → test → build-all` smoke to exit zero **without GPU hardware**, so any tests that hit autograd through tensor ops on the GPU MUST skip cleanly when no WebGPU adapter is available — same `describe.skipIf(!webgpuAvailable)` gating as `gpu-bootstrap`, `core-wgsl-kernels`, `reduction-norm-kernels`, and `tensor-bootstrap`.
- **`tensor-bootstrap`** functional surface is the only allowed forward route — autograd MUST NOT import `@llm-transformer-diy/gpu` directly and MUST NOT touch `GPUBuffer` outside what `Tensor` already exposes.
- **`docs/project.md` GPU-only stance** — autograd inherits the "fail loudly with no adapter" policy via tensor's behavior; autograd adds no CPU fallback.
- **Layering** — `packages/autograd` MUST NOT add upward dependencies and MUST NOT touch `packages/tensor` or `packages/gpu` source in this scope. The new public surface stays consumable from a future `model` / `training` change without renaming.

## Goals / Non-Goals

**Goals:**

- Replace the autograd stub with a real **define-by-run** engine: `Variable` records, `Operation` interface, topological `backward` traversal, `Parameter` leaf, `ParameterRegistry` with `registerParameter` / `parameters` / `zeroGrad` / `totalParams`.
- Wire **forward + backward** for the trivially-derivable ops: `add`, `mul`, `scale`, `transpose`, `reshape`. Every backward routes through the existing `@llm-transformer-diy/tensor` functional surface — **no new GPU kernels** in this change.
- Allocate the initial `output.grad` as a ones-filled tensor when `backward(rt, output)` is called and the caller has not pre-set `output.grad`; this matches the standard `loss.backward()` convention from `docs/project.md` Component 3.
- Verify correctness with **finite-difference gradient checks** on a tiny composed graph (rank-2, ≤ 12 elements per tensor) using **only** the trivially-derivable ops in scope.
- Keep the public surface **strictly additive**: existing `AUTOGRAD_LAYER_MARKER` and `__autogradDependsOnTensor` remain importable until a downstream consumer is migrated off them. (`packages/model` is still a stub at the time of this change; we leave the markers in place for now and a later cleanup change drops them once nothing in the workspace imports them.)
- Match `packages/tensor`'s functional style: no class declarations, no methods on records, no module-level mutable state besides a private monotonic id counter scoped to `variable.ts`.

**Non-Goals:**

- **`matmul` backward.** Lands in a follow-up change; it needs `tensor.matmul` + `tensor.transpose` with shape choreography (`dA = dC @ B^T`, `dB = A^T @ dC`) plus a numeric test that exercises non-square shapes. Keeping it out of this change preserves the "trivially-derivable only" framing and the diff size.
- **`gelu` backward.** Needs the GELU derivative (tanh-formulation) — either a new WGSL backward kernel or a CPU-derivative-then-upload helper. Lands pairwise with its forward analysis.
- **`softmax` backward.** Jacobian-vector product against the cached forward output. Lands pairwise.
- **`rmsnorm` backward.** Chain rule through the `1 / sqrt(mean(x²) + ε)` factor with a learned gamma; needs a fused kernel or carefully composed tensor ops. Lands pairwise.
- **`embedding`** (gather forward / scatter-add backward) and **`cross_entropy`** (combined softmax + NLL grad) — `docs/sequential-change-proposals.md` step 6.
- **Optimizer kernels** (`adamw`, `clip_norm`) — step 7.
- **Broadcasting** in autograd op wrappers (input shapes must already match what `tensor.*` requires).
- **Higher-order derivatives** (`grad-of-grad`).
- **Automatic intermediate-tensor reclamation.** Tests destroy explicitly; production callers manage lifetime per the `tensor-bootstrap` policy.
- **A `retain_graph` flag.** Each `backward` call traverses the graph as recorded; calling `backward` twice on the same graph without zero-ing intermediate `.grad` fields is documented behavior, not an error.
- **`requiresGrad` toggling at runtime.** `requiresGrad` is set at leaf-construction time and propagated by op wrappers; there is no `setRequiresGrad`.
- **Edits to `packages/tensor` or `packages/gpu`.**

## Decisions

| Decision                                                                                                                                                                                                                                                                                                         | Rationale                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Functional records + free functions; no `class Variable` / `class Operation` / `class ParameterRegistry`.**                                                                                                                                                                                                    | Matches `packages/tensor` immediately below and `docs/guidelines/typescript.md`'s "functional first" stance. Class hierarchies are not needed for define-by-run. The single intentional mutability (`Variable.grad`) is concentrated in one helper and documented as the only mutable field in the package.                                                                                 |
| **`Variable.grad` is the only mutable field. All other fields are `readonly`.**                                                                                                                                                                                                                                  | Backward must accumulate; making `grad` the single mutable slot scoped behind `accumulateGrad` keeps the surface analyzable and matches PyTorch's `Variable.grad` convention without exposing more mutability.                                                                                                                                                                              |
| **`Operation` is a closure created at forward time, bound to its inputs.** Each forward op (`addV`, `mulV`, …) constructs an `Operation` whose `backward(rt, gradOutput)` returns one `Tensor` per input position (or `null` when the input does not require grad).                                              | Avoids the indirection of "operation factory + bound state record" pairs. Closure capture is the simplest representation of "this is the local Jacobian × gradOutput formula for these specific inputs".                                                                                                                                                                                    |
| **`Variable.id` is a monotonic `number` from a module-private counter in `variable.ts`.** No `Variable.id` collisions across runs in a single Node.js process.                                                                                                                                                   | The topo traversal needs a stable, hashable identity for de-duplication. Object identity via `Set<Variable>` works but is harder to debug; a numeric id is grep-friendly and prints cleanly in test failures. Counter is reset only on process restart, which is acceptable since graph traversal is per-call.                                                                              |
| **`Variable.parents` mirrors `Variable.creator?.inputs`.** Stored on the variable to keep the topo walk a one-pointer hop instead of `v.creator?.inputs ?? []`.                                                                                                                                                  | Tiny memory cost; substantially simpler traversal code; avoids a `null` check in the inner loop. Equivalent semantically because `Operation.inputs` is set once at construction.                                                                                                                                                                                                            |
| **`backward(rt, output)` allocates `output.grad` as ones-of-shape if `output.grad === null`.** Caller can pre-set `output.grad` to seed a different upstream gradient.                                                                                                                                           | Matches `loss.backward()` from `docs/project.md` Component 3. Falling back to ones lets the finite-difference test compare to the gradient of `Σ output` per parameter element, which is the standard practice.                                                                                                                                                                             |
| **Topological order is computed via post-order DFS with a visited set keyed by `Variable.id`.** Walked in reverse for backward.                                                                                                                                                                                  | Standard textbook approach. Single pass, O(V + E). De-duplication ensures a `Variable` reached via multiple paths gets backward called once.                                                                                                                                                                                                                                                |
| **Gradient accumulation uses `tensor.add` (not in-place), allocating a fresh GPU buffer per accumulation step.** When the input's `.grad` is currently `null`, the contribution is **assigned directly** without copy.                                                                                           | `tensor` does not yet support in-place ops, and adding `addInPlace` here would either touch `packages/tensor` (out of scope) or invent a new mutation path. Allocating fresh buffers per accumulation is correctness-first; a future perf pass can fuse accumulation. The "first contribution = direct assignment" branch avoids a wasted `add(zero, grad)` on the common single-path case. |
| **`requiresGrad` propagates as `inputs.some(i => i.requiresGrad)`.** When no input requires grad, the op wrapper returns a leaf-style Variable (`creator: null`, `requiresGrad: false`) — the forward computation still runs, but no graph node is recorded.                                                     | Mirrors PyTorch. Avoids recording a graph for read-only constant chains (e.g. when computing a fixed positional embedding outside a parameter path), which keeps memory usage proportional to the trainable graph rather than the entire forward computation.                                                                                                                               |
| **`reshape` autograd wrapper has no `rt` parameter** and the resulting `Variable.tensor` shares its buffer with the input. Backward emits `tensor.reshape(gradOut, originalShape)` (also buffer-shared at the tensor layer).                                                                                     | Mirrors `tensor.reshape`'s pure-metadata contract. The shared buffer is a deliberate consequence of `tensor.reshape`'s semantics; documented in JSDoc on the autograd wrapper.                                                                                                                                                                                                              |
| **`ParameterRegistry` is a `readonly` record `{ params: Parameter[] }` whose `params` array is mutated only via `registerParameter`.** No `Set` for deduplication; no removal helper.                                                                                                                            | Matches the registry's role as an append-only collection during model construction. Removal would imply mid-training parameter pruning, which is out of scope. The mutable-array-inside-a-readonly-record pattern is consistent with how `KernelRegistry` works in `packages/gpu` (a registry holds a private `Map`).                                                                       |
| **`zeroGrad(reg)` sets each parameter's `.grad = null`.** It does **not** allocate a zero tensor.                                                                                                                                                                                                                | `null` is the explicit "no contribution yet" state used by `accumulateGrad`'s "first contribution = direct assignment" branch. Allocating a zero tensor every step would double the GPU memory traffic for gradient accumulation with no benefit. Future optimizer kernels can pre-allocate `.grad` once and reuse the buffer; that change can revisit this decision.                       |
| **`totalParams(reg): number` returns the sum of `p.tensor.length` across all registered parameters.**                                                                                                                                                                                                            | Matches `docs/project.md` Component 3's "count for display" semantics. No element-type weighting (everything is `f32` in this scope).                                                                                                                                                                                                                                                       |
| **No `clipGradNorm` in `ParameterRegistry`.**                                                                                                                                                                                                                                                                    | Per the user's scope: deferred to the optimizer change. Adding it here would either pull in `core.reduce_sum` plumbing (extra surface to validate) or invent a CPU readback path that conflicts with the GPU-only stance.                                                                                                                                                                   |
| **Op wrappers re-use plain names (`add`, `mul`, `scale`, `transpose`, `reshape`) inside `@llm-transformer-diy/autograd`.** Tensor and Variable are different types so static type-checking flags misuses; the package name disambiguates at call sites (`autograd.add(rt, va, vb)` vs `tensor.add(rt, ta, tb)`). | Matches `tensor`'s precedent of reusing op names from kernels. Avoids a parallel naming scheme (`addV` / `addOp`) that would diverge from PyTorch / JAX user expectations and from `docs/project.md`'s sketch.                                                                                                                                                                              |
| **Pure unit tests use throwaway fake Variables / fake parameters whose `tensor` field is a `{ shape, length }` shape stub for the topo-order and `totalParams` tests.** GPU-gated tests build real `Tensor` records via `createFromArray`.                                                                       | Same split that `tensor-bootstrap` used (pure `shape.spec.ts` + GPU-gated `tensor.spec.ts`). Keeps the no-WebGPU run fast and lets pure logic regress independently of GPU availability.                                                                                                                                                                                                    |
| **The finite-difference test runs on a fixed composed graph** (e.g. `f = scale(reshape(mul(add(a, b), c), [n]), 2.0)`) over inputs of shape `[2, 3]`. Numerical gradient: central difference with `ε = 1e-3`; tolerance `5e-3` on max absolute difference.                                                       | `ε = 1e-3` is large enough to avoid `f32` round-off and small enough that the truncation error of central difference is negligible at this scale. `5e-3` tolerance accommodates `f32` precision on per-element differences for a graph of this depth.                                                                                                                                       |
| **Tests reuse the existing `webgpuAvailable` probe / runtime construction pattern** from `tensor-bootstrap` rather than introducing a parallel test harness.                                                                                                                                                     | Single source of truth for "is the GPU usable here"; consistent skip behavior across packages.                                                                                                                                                                                                                                                                                              |

**Alternatives considered:**

- **Class-based `Variable` / `Operation` / `ParameterRegistry`** matching `docs/project.md` Component 3 verbatim. Rejected: inconsistent with `packages/tensor`'s functional shape and with `docs/guidelines/typescript.md`'s "functional first". `docs/project.md` is a sketch; the design decision on shape lives in the change proposal.
- **Tape-based autograd** (a global `GradientTape` records ops, then walks the tape in reverse). Rejected: adds module-level mutable state and complicates parallel forward passes (tape stacking). Define-by-run with creator pointers is the standard approach for educational autograds.
- **Storing the backward closure as a function (`(gradOut) => grads`)** rather than wrapping it in an `Operation` record with a `name` field. Rejected: the `name` field is meaningful for debugging (graph dumps, error messages) and the cost of one extra string allocation per node is negligible.
- **Eager gradient accumulation via in-place tensor add.** Rejected: tensor layer does not expose in-place ops, and adding one solely for this would expand `tensor`'s surface. Out-of-place accumulation is correct; perf revisits later.
- **Skipping the leaf-style fast path when no input requires grad** and always recording a graph node. Rejected: every forward call would record a node, including those that compute constants — wasteful for inference paths once the model layer lands.
- **Including `matmul` with backward in this change.** Rejected: explicit user instruction; `matmul` backward needs the `dA = dC @ B^T` / `dB = A^T @ dC` choreography plus a focused numeric test, which is the right size for its own change.
- **Adding `gelu` with a derivative-on-CPU shim.** Rejected: the derivative formula needs to be either a new WGSL kernel or a `tensor.geluBackward` helper; either path expands `tensor` or `gpu`. Defer to a pairwise change.

## Risks / Trade-offs

- **[Risk] `Variable.grad` mutability could leak into other paths.** Mitigation: only `accumulateGrad` writes to `Variable.grad`; documented at the type level (`grad` is the only non-`readonly` field) and reinforced by a structural ESLint rule check via the existing strict-TS settings (mutating any other field would surface as a TS error against the `readonly` declarations). The grep audit `\.grad\s*=` should match only inside `accumulateGrad` and `zeroGrad`.
- **[Risk] Out-of-place gradient accumulation allocates fresh GPU buffers every step.** Mitigation: documented; the optimizer change will revisit either by adding an in-place add to `tensor` or by preallocating `.grad` buffers and using a fused update kernel. For training a `tiny` config, the per-step buffer churn is well under the WebGPU memory budget.
- **[Risk] Fresh `Variable.id` counter resets per process; cross-process graph identity is undefined.** Mitigation: documented; the autograd graph never crosses a process boundary in this project (no IPC autograd), so process-scoped uniqueness is sufficient. Tests assert id uniqueness within a single process only.
- **[Risk] The finite-difference test is sensitive to `f32` precision.** Mitigation: `ε = 1e-3` central difference balances truncation vs round-off; tolerance `5e-3` is empirically wide enough for the shapes in scope. If the test flakes, the tolerance is easy to relax in a follow-up; the current value is a starting estimate based on `tensor`'s existing CPU-vs-GPU `1e-5` tolerance scaled by graph depth.
- **[Risk] Calling `backward` twice on the same graph without `zeroGrad` doubles existing `.grad` values.** Mitigation: this is documented behavior matching PyTorch's default. Tests for `backward` always pair with a prior `zeroGrad(reg)` call. We do not enforce single-call semantics.
- **[Risk] `requiresGrad: false` propagation may hide bugs where a parameter is unintentionally constructed without `requiresGrad`.** Mitigation: `createParameter(tensor)` sets `requiresGrad: true` by construction (no overload that sets it false). Consumers cannot accidentally make a non-trainable parameter via the documented constructor; they would have to call `createLeafVariable(tensor, false)` explicitly.
- **[Risk] Stub markers (`AUTOGRAD_LAYER_MARKER`, `__autogradDependsOnTensor`) remaining in the public surface.** Mitigation: kept in this change for backwards compatibility with the workspace's existing `model` stub (if any imports them); a follow-up cleanup change drops them once unused. Same staging that `tensor-bootstrap` used for `TENSOR_LAYER_MARKER`.
- **[Risk] The trivially-derivable scope is so small it cannot exercise interesting backward shapes.** Mitigation: the finite-difference test composes `add` + `mul` + `scale` + `reshape` over rank-2 tensors so backward must thread through reshape and out — non-trivial enough to catch topo-order regressions. The narrow scope is the point: each subsequent change adds one op's backward with focused tests.

## Migration Plan

- **Deploy**: Replace `packages/autograd/src/index.ts` stub with real exports across new modules (`types.ts`, `variable.ts`, `backward.ts`, `parameter-registry.ts`, `ops.ts`). Keep `AUTOGRAD_LAYER_MARKER` / `__autogradDependsOnTensor` exports until a downstream consumer is migrated off them. No edits to `packages/tensor` or `packages/gpu`. No new npm dependencies. Existing tests in `packages/tensor` and `packages/gpu` continue to pass unchanged.
- **Rollback**: Revert `packages/autograd` commits; `tensor`, `gpu`, `model`, `training`, and `inference` are unaffected because none of them import the new autograd surface yet.

## Open Questions

- **Spec file split**: do the autograd unit tests live in a single `autograd.spec.ts` plus `backward.spec.ts` for the GPU-gated finite-difference checks, or in per-module `*.spec.ts` mirroring tensor's `shape.spec.ts` / `reshape.spec.ts` / `tensor.spec.ts` split? Tasks should pick **one** based on file length after implementation; both are valid.
- **Where the monotonic id counter lives**: a module-private `let nextVariableId = 0` at the top of `variable.ts` is the simplest implementation but introduces module-level mutable state — the only such state in the package. The alternative (passing an id allocator through `TensorRuntime` or a new `AutogradContext`) increases surface for negligible benefit. Proposal favors the module-private counter; reviewers may prefer an explicit allocator and that is a 5-minute refactor.
- **Whether to record `Variable.parents` separately from `Variable.creator?.inputs`** or compute it on demand. Proposal stores it for traversal simplicity; if profiling later shows the redundancy matters, drop it without a public API change.
- **Whether `parameters(reg)` returns a defensive `[...reg.params]` copy or a `readonly Parameter[]` view of the internal array.** Defensive copy is safer; `readonly` view is cheaper. Proposal picks defensive copy and notes the trade-off in JSDoc.
