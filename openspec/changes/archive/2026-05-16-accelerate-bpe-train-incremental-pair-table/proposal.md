# Proposal: Accelerate BPE training with an incremental pair table

## Why

`BPETokenizer.trainFromFiles` (disk-stream) and `trainAsyncOnUtf8Bytes` / `train` (RAM) are the user-visible long pole on real corpora: training a vocabulary of ~10 000 merges on a 300 MB corpus runs for **hours** with ~1 of 32 cores busy, RAM essentially flat, and disk effectively idle. The cause is structural, not constants:

- The merge loop is `O(N · M)` (`N` = byte-tokens, `M` = merges). Every iteration re-scans the entire token stream **once** to build a pair-frequency map (`countAdjacentPairsOverlappingUint32` / `countAdjacentPairsFromU32LeTokenFile`) and **again** to rewrite every occurrence of the chosen pair (`rewriteGreedy` / `rewriteGreedyU32LeTokenFile`). For 300 MB × 10 000 merges this is `≈ 6 × 10¹²` token visits.
- Each visit pays a heavy per-pair string allocation: `bpePairKey(L, R)` allocates a fresh `${L}\0${R}` string for **every adjacent pair** and uses it as a `Map<string, number>` key. On a 300 MB corpus that is `≈ 3 × 10¹²` short-lived strings over the run.
- The disk-stream path additionally pays one `await` (i.e. one Promise + microtask + closure) **per token** in both `pipelineReadStreamToTokens` and `rewriteGreedyU32LeTokenFile.nextU32` — order `10¹²` microtasks total for a 300 MB / 10 000-merge run.

The published research note `docs/research/bpe-encode-throughput.md` already lists the algorithmic fix (priority-queue + linked-list with **incremental pair-frequency maintenance**, the SentencePiece / Sennrich PR #1208 design) as the highest-ROI lever, and confirms `worker_threads` does not help unless the algorithmic ceiling is removed first. This proposal lifts the train path to a **single-thread `O(N + M · log N + ΣKₘ)`** algorithm (`Kₘ` = occurrences of the merge chosen at step `m`), eliminates the per-pair string keys, and removes the per-token `await` storm — keeping the change strictly inside `packages/tokenizer` with no new dependencies, no `worker_threads`, no GPU work, and **bit-identical merge tables** for any input.

## What Changes

- **Replace the per-merge full re-scan with an incremental pair-frequency table.** A new private `BpePairFreqIndex` data structure tracks, for each `(L, R)` pair seen in the working stream, both the current count and the set of stream positions where it occurs. After each merge of pair `P` at position `i`, only the **four affected adjacencies** are mutated:
  - decrement `count` for the at-most-three existing pairs `(prev, L)`, `(L, R)` (= `P` itself, removed), and `(R, next)` at site `i`;
  - increment `count` for the at-most-two new pairs `(prev, mergedId)` and `(mergedId, next)`;
  - update each pair's position set so the next "best pair → all occurrences" step can iterate occurrences in `O(Kₘ)` instead of scanning `N`.
- **Replace `Map<string, number>` keyed by `bpePairKey` with a typed-array open-addressing hashmap keyed by `(L, R)` numerically.** Pairs are encoded as a single `BigInt` `(BigInt(L) << 32n) | BigInt(R)` for the public surface where pair identity is exposed (e.g. `pickBestMergePair`), and as parallel `Uint32Array`s (`keysL`, `keysR`, `counts`) inside the index for the inner loop, so the hot path performs zero per-pair allocations.
- **Replace the working `Uint32Array` token stream + `rewriteGreedy(...) → new Uint32Array` cycle with a doubly-linked list of token "slots".** Slots are stored as parallel `Uint32Array`s (`value`, `prev`, `next`, `alive`), pre-allocated to length `N` (the initial byte count) and never reallocated; merges turn two adjacent live slots into one slot in `O(1)`. Final extraction (or partial extraction during disk-stream initialization) walks the live list once.
- **Replace the disk-stream "rewrite the full `u32` file per merge" loop with a one-shot disk → in-RAM linked-list materialization.** `trainFromFiles` SHALL stream-read the joined corpus once into the linked-list slots (`O(N)` reads, no per-merge file I/O), run the same incremental merge loop as `trainAsyncOnUtf8Bytes`, and skip the per-merge `await rewriteGreedyU32LeTokenFile(...)` + `await stat(...)` round-trip entirely. The `--disk-stream` CLI flag remains as the path that **avoids the giant in-RAM `Buffer` concat in `concatCorpusAsUtf8Bytes`** but no longer implies on-disk per-merge rewrites; its meaning is now "stream the corpus from disk during the initial materialization step" rather than "perform every merge as a file rewrite".
- **Remove the per-token `await` storm in the disk-stream materializer.** `pipelineReadStreamToTokens` SHALL push tokens into the linked-list slot arrays in **bulk per-chunk** (one synchronous loop per `Buffer` chunk emitted by the read stream), with at most one `await` per chunk for cooperative yielding — not one per byte.
- **`trainAsyncOnUtf8Bytes` keeps its existing yield contract** (`yieldToHost?` between merges, plus the existing stripe-yield during the initial UTF-8 → token-stream materialization). With incremental maintenance the per-merge step is now `O(Kₘ)` instead of `O(N)`, so the same yield cadence delivers far better TUI responsiveness for free.
- **Hooks expand to expose the new dominant cost.** `BpeTrainFromFilesHooks` and `BpeTrainHooks` gain an optional `onPairIndexBuilt(initialDistinctPairs: number)` callback fired once after the initial pair index is constructed, so the wolf-tui dashboard can switch from "scanning corpus" to "merging" with an accurate denominator. Existing hooks (`onCorpusUtf8Bytes`, `onMergeComplete`, `onTokenStreamBytesWritten`, `yieldToHost`) keep their current contract; `onTokenStreamBytesWritten` reports the size of the **initial** materialized linked-list footprint (one final value when materialization completes) instead of per-merge file growth.
- **Bit-identical merge output.** For every input corpus and every `vocabSize`, the new training path SHALL produce the same ordered `merges` list and the same `vocab` byte rows as the current path. This is the same equivalence argument the archived `optimize-bpe-encode-hot-loop` change relied on: greedy maximum-count selection with `(smaller L, smaller R)` tie-break is uniquely defined per iteration, so any data structure that tracks the same `(L, R) → count` map and applies the same merge rule produces the same trace.

This is an **internal performance change**. The on-disk tokenizer JSON format (`kind`, `version`, `merges`, `vocab`) is unchanged; existing `tokenizer.json` files load and produce identical token sequences after this change. No new dependencies, no `worker_threads`, no GPU work — strictly within `packages/tokenizer` plus a tiny TUI label adjustment in `apps/cli/src/cmd/tokenizer-train.tsx`.

Out of scope (kept as separate follow-up changes per `docs/research/bpe-encode-throughput.md` staging):

- Pre-tokenization (regex / whitespace+punctuation). That is a tokenizer **format** change.
- `worker_threads` parallel pair counting and parallel encode. With incremental maintenance the per-merge step is bound by `Kₘ` not `N`, so worker speedups become a follow-up optimization on top of this change.
- WGSL / GPU BPE.
- Encode-time changes — the `optimize-bpe-encode-hot-loop` change already shipped the encode-side wins; this change is strictly about **training**.

## Capabilities

### New Capabilities

- _(none)_

### Modified Capabilities

- `tokenizer-bpe-bootstrap`: Generalize the **Deterministic byte-level BPE training** requirement so it prescribes the **observable merge sequence and final vocabulary** (which are unchanged) without mandating the per-iteration full-stream re-scan and full-stream rewrite as the implementation. Add a new **Incremental pair-frequency maintenance during training** requirement that pins the algorithmic invariants (incremental update of pair counts on each merge, occurrence tracking sufficient to enumerate merge sites in `O(Kₘ)`) and asserts merge-trace equivalence with the original full-rescan algorithm. Update the disk-streamed training requirement so it describes corpus materialization (one streaming pass) instead of per-merge file rewrites.

## Impact

- **`packages/tokenizer/src/bpe-tokenizer.ts`**: Replace `RamBpeRunner.stream: Uint32Array` with a linked-list slot representation; replace `ramBpeMergeOneStep` with a step that consults a `BpePairFreqIndex` and performs `O(Kₘ)` slot edits + index updates; rewrite `trainFromFiles` to materialize once and re-use the same incremental loop; thread `onPairIndexBuilt` through `BpeTrainHooks` / `BpeTrainFromFilesHooks`. The public class surface (`train`, `trainAsync`, `trainAsyncOnUtf8Bytes`, `trainFromFiles`, `encode`, `encodeAsync`, `encodeUint32`, `encodeUint32Async`, `decode`, `save`, `load`, `vocabSize`) and the JSON shape stay the same.
- **`packages/tokenizer/src/bpe-merge-stats.ts`**: `bpePairKey`, `countAdjacentPairsOverlappingUint32`, and `countAdjacentPairsFromU32LeTokenFile` are no longer called from the training hot path. We keep them exported for backward-compatibility (and for the equivalence-test harness in §Tests) but mark them `@deprecated` for hot-path use; they remain useful as a reference / golden oracle.
- **`packages/tokenizer/src/bpe-train-disk.ts`**: `rewriteGreedyU32LeTokenFile` is no longer used by `trainFromFiles`. `writeJoinedCorpusAsTokenIdsToFile` is replaced by an internal `streamCorpusIntoLinkedList(...)` helper; we keep `writeJoinedCorpusAsTokenIdsToFile` exported (still needed for tests / inspection tooling) but remove its `await flushToken` per-byte loop in favor of bulk-push-per-chunk.
- **`apps/cli/src/cmd/tokenizer-train.tsx`**: TUI labels in `TokTrainView` change to reflect that the disk-stream path no longer rewrites the token file every merge. The `tokenStreamFileMiB` field becomes the **post-materialization** size and is shown only once during the `materialize` phase. `--disk-stream` flag, command surface, and exit codes remain unchanged. New optional `onPairIndexBuilt` is wired through but not surfaced as a separate phase if it would clutter the layout — it is enough to thread it for future use.
- **Tests**: Existing `packages/tokenizer/src/bpe-tokenizer.spec.ts` (round-trip, tie corpus, save/load, untrained errors) keeps passing unchanged; `packages/tokenizer/src/__tests__/bpe-encode-hot-loop.spec.ts` keeps passing unchanged. Add a **train-equivalence** spec that runs the legacy `Map<string, number>` + full-rescan training in-process against the new incremental training on at least: (a) the `corpus/real/` Hamlet sample, (b) a synthetic worst-case repetition corpus (`"abababab…"`-style), (c) a UTF-8 multibyte corpus (`"héllo 世界"` repeated), and asserts identical ordered `merges` and identical `vocab` byte rows for `vocabSize ∈ {S+260, S+1024}`. Add a synthetic-large-corpus benchmark (skipped in CI by default) that records wall time and merges/sec for the new path on a ~10 MB synthetic corpus.
- **Performance / memory**: Train-path peak RAM rises from `~4N` bytes (`Uint32Array` token stream) to `~16N` bytes (four `Uint32Array`s of length `N` for the linked-list slots) plus the pair index (bounded by **distinct** adjacent pairs, typically `≪ N`). For a 300 MB corpus this is `~4.8 GiB`, comfortably below the 32 GiB-class machines this targets; for the in-memory `train` path callers who hit RAM limits there is no regression versus today (today the path already requires `~4N` for the stream plus transient `~4N` for each `rewriteGreedy` allocation = `~8N` peak). Train wall time on representative corpora is expected to drop from `O(N · M)` to `O(N + M · log N + ΣKₘ)` — for the user's reported 300 MB / ~10 000-merge case, hours → low minutes.
- **No API breaks.** The `Tokenizer` interface, the `BPETokenizer` class surface, and the on-disk `tokenizer.json` format are unchanged. Existing checkpoints, existing on-disk token caches, and existing CLI flags continue to work without migration.
- **No new dependencies.** Implementation is pure TypeScript on top of `Uint32Array` / `BigInt` primitives, in keeping with the "own the stack" mandate in `docs/project.md`.
